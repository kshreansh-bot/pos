1. Architecture Overview

The billing engine is the core POS functionality that converts cart items into legally compliant invoices. It operates as a tightly coordinated system with three primary concerns:

Transaction Atomicity

Single database transaction encompassing validation, creation, stock deduction, and ledger recording. All or nothing.

Data Immutability

Invoice snapshots preserve product data at time of sale, preventing retroactive changes to pricing or tax rates.

Tax Compliance

Prices are GST-inclusive; tax is extracted per line by rate, grouped for reporting.

Public Access

QR code directs to rate-limited public bill page with no authentication required.

High-Level Components

Component Responsibility Scope
BillingService Orchestrates invoice creation with business logic Service layer; handles all validation and coordination
TaxCalculator Extracts tax from GST-inclusive prices by rate Pure function; testable, reusable
QRTokenGenerator Generates cryptographically random 128-bit tokens Utility; non-sequential, non-enumerable
InvoiceAPI HTTP routes for invoice creation and retrieval API layer; role-based access control
PublicBillAPI Rate-limited public endpoint for bill viewing API layer; no authentication, token-based access

2. BillingService Design

Core Methods

create_invoice()

async def create_invoice( session: AsyncSession, customer_id: Optional[int], user_id: int, items: List[InvoiceItemRequest], payment_method: str, discount_percent_bill: int = 0, amount_tendered_paise: Optional[int] = None, notes: Optional[str] = None ) -> Invoice

Purpose: Orchestrates the complete invoice creation flow with atomic transaction semantics.

Business Logic

  1. Validate inputs – payment method, discount limits, customer exists
  2. Fetch current product data – prices, tax rates, availability
  3. Allocate stock – FEFO logic per product, check expiry dates
  4. Calculate totals – per-line tax extraction, discount application
  5. Create invoice – atomic: insert invoice + items + stock movements
  6. Generate QR token – random 128-bit, ensure uniqueness
  7. Return complete invoice – with all snapshots and ledger entries

cancel_invoice()

async def cancel_invoice( session: AsyncSession, invoice_id: int, user_id: int, reason: str ) -> Invoice

Purpose: Reverses an invoice, returning stock to inventory and creating reversing stock movements.

Business Logic

  • Only completed invoices can be cancelled
  • For each invoice item, return quantity to batch with FEFO re-sorting
  • Create reversing stock movements with audit trail
  • Mark invoice as CANCELLED, keep original data intact
  • Record audit log with cancellation reason

apply_item_discount()

async def apply_item_discount( session: AsyncSession, product_id: int, discount_percent: int, user_id: int ) -> bool

Purpose: Validates cashier discount limits before applying line-item discount.

Validation Rules

  • Discount percent must be 0-100
  • User's max_discount_percent from User.max_discount_percent
  • Manager role can override cashier limits (role-based in API)
  • Return true if allowed, raise ValidationError if not

get_invoice_by_public_token()

async def get_invoice_by_public_token( session: AsyncSession, public_token: str ) -> Optional[Invoice]

Purpose: Retrieve invoice by its unique QR token for public bill page.

  • No authentication required
  • Return complete invoice with all items and tax breakdown
  • Include customer name only if set; never expose customer contact details publicly

3. Invoice Schema & Snapshots

Schema Design Philosophy

Invoice snapshots are immutable copies of product data taken at time of sale. This prevents retroactive price changes from affecting historical invoices' tax calculations and printed bills.

InvoiceItem Snapshot Fields

Product Snapshot (copied from Product model)

  • product_name – From Product.name
  • product_barcode – From Product.barcode
  • product_unit – From Product.unit (e.g., "kg", "liter")

Pricing & Tax Snapshot (captured at sale time)

  • unit_price_paise – Product.selling_price_paise at time of sale (GST-inclusive)
  • gst_rate – From Product.gst_rate (0, 5, 12, 18, or 28)
  • tax_amount_paise – Extracted via tax calculation formula
  • discount_percent – Applied discount at line level
  • discount_paise – Discount amount in paise

Line Totals

  • quantity – Units sold
  • line_total_paise – (unit_price_paise × quantity) - discount_paise

Inventory Linkage

  • batch_id – Foreign key to StockBatch (nullable if no expiry tracking)
  • product_id – Foreign key to Product (for audit trail only)

Invoice Header Fields

Field Type Purpose
invoice_number String (50) Format: INV-YYYY-NNNNNN (e.g., INV-2026-000001), unique, sequential per year
public_token String (32) Random 128-bit hex token (not sequential), links to QR code
customer_id Int (nullable) Link to Customer for loyalty; null for walk-in customers
user_id Int Cashier who created invoice
payment_method String One of: cash, card, upi
status Enum completed, cancelled, returned

Financial Summary Fields

All amounts stored as paise (integer)

  • subtotal_paise – Sum of (unit_price × qty) before any discount or tax extraction
  • total_discount_paise – Sum of line discounts + bill-level discount
  • total_tax_paise – Sum of extracted taxes by rate
  • total_amount_paise – subtotal - discount (tax is implicit in prices)

Payment Fields

Field When Required Purpose
amount_tendered_paise For cash payments Amount customer paid (for change calculation)
change_due_paise For cash payments Calculated as amount_tendered - total_amount

4. Tax Calculation Algorithm

Principle: GST-Inclusive Pricing

All prices in the system are GST-inclusive (the displayed/selling price includes tax). The algorithm extracts tax from this inclusive price.

Tax Extraction Formula

// Given: // unit_price_paise (GST-inclusive price customer pays) // gst_rate (0, 5, 12, 18, or 28) // quantity // Tax amount per unit: tax_per_unit = (unit_price_paise × gst_rate) ÷ (100 + gst_rate) // Base price per unit (excluding tax): base_per_unit = unit_price_paise - tax_per_unit // For a line: line_quantity = quantity line_tax = (tax_per_unit × line_quantity) line_base = (base_per_unit × line_quantity) line_inclusive = line_base + line_tax // Verify: line_inclusive ≈ (unit_price_paise × line_quantity)

Example Calculation

Product: 1 kg Wheat Flour @ INR 180/kg (18% GST)

unit_price_paise = 18000 (INR 180.00, GST-inclusive) gst_rate = 18% tax_per_unit = (18000 × 18) ÷ (100 + 18) = 324000 ÷ 118 = 2745.76... paise ≈ 2746 paise (rounded) base_per_unit = 18000 - 2746 = 15254 paise For quantity = 2: line_tax = 2746 × 2 = 5492 paise (INR 54.92) line_base = 15254 × 2 = 30508 paise (INR 305.08) line_inclusive = 30508 + 5492 = 36000 paise (INR 360.00) Verify: 18000 × 2 = 36000 ✓

Rounding Strategy

Critical for accuracy

  • Per-unit tax: Round to nearest paise using standard banker's rounding
  • Per-line tax: Sum of (tax_per_unit × qty), not (tax_total ÷ qty)
  • Invoice total: Sum of all line taxes; slight discrepancy from manual calculation expected
  • Report verification: Verify taxes group correctly by rate, not individual line exactness

Tax Grouping by Rate

After all items are added, group taxes by GST rate for reporting and compliance:

tax_breakdown = { 0: { rate: 0, amount_paise: 0 }, 5: { rate: 5, amount_paise: X }, 12: { rate: 12, amount_paise: Y }, 18: { rate: 18, amount_paise: Z }, 28: { rate: 28, amount_paise: W } } Sum for each rate: 0% tax: sum(line_tax where gst_rate == 0) 5% tax: sum(line_tax where gst_rate == 5) ... etc

TaxCalculator Service Class

class TaxCalculator: @staticmethod def extract_tax(unit_price_paise: int, gst_rate: int) -> int: """Extract tax from GST-inclusive price.""" @staticmethod def calculate_line_tax(unit_price_paise: int, gst_rate: int, quantity: int) -> int: """Calculate tax for a line item.""" @staticmethod def group_taxes(invoice_items: List[InvoiceItem]) -> Dict[int, int]: """Group taxes by rate from invoice items."""

Discount Application Logic

Line-Level Discount

Applied after tax is extracted, on the GST-inclusive price:

discount_paise = (unit_price_paise × quantity × discount_percent) ÷ 100 line_total_paise = (unit_price_paise × quantity) - discount_paise

Bill-Level Discount

Applied to invoice subtotal (sum of line totals before bill discount):

bill_discount_paise = (subtotal_paise × discount_percent_bill) ÷ 100 final_total_paise = subtotal_paise - bill_discount_paise

5. QR Token Generation Strategy

Token Specification

Property Value Rationale
Size 128 bits (16 bytes) Industry standard; provides ~10^38 possible values
Encoding Hexadecimal (32 chars) URL-safe, easily printed/scanned, database-friendly
Generation Cryptographically random Not sequential; prevents enumeration attacks
Collision Handling Retry with exponential backoff Retry up to 5 times; fail if collision persists

QRTokenGenerator Implementation

class QRTokenGenerator: MAX_RETRIES = 5 @staticmethod async def generate_unique_token(session: AsyncSession) -> str: """Generate unique 128-bit hex token."""
Algorithm: generate_unique_token() for attempt = 0 to MAX_RETRIES: token = random_hex(128 bits / 4 = 32 hex chars) // Check uniqueness existing = Query(Invoice).filter(public_token == token).first() if existing is None: return token // Exponential backoff: 10ms × 2^attempt sleep(10ms × 2^attempt) raise DataIntegrityError("Failed to generate unique token after retries")

QR Code Format

Suggested QR Code URL

https://your-domain.com/bills/{public_token} or https://your-domain.com/api/v1/public/bills/{public_token}

QR Code Metadata (optional)

Include in QR code data or as separate fields:

  • Invoice number (for customer reference)
  • Invoice date/time
  • Total amount (for quick verification)

Token Uniqueness Guarantee

  • Database constraint: UNIQUE(public_token) on Invoice table
  • Application retry logic with exponential backoff
  • Probability of collision over 10 million invoices: ~10^-15 (negligible)

6. Public Bill Page API Design

API Endpoint Specification

GET /api/v1/public/bills/{public_token}

Request

  • No authentication required
  • public_token: 32-char hex string (from QR code)

Response (200 OK)

{ "invoice_number": "INV-2026-000001", "created_at": "2026-10-01T14:30:00Z", "customer_name": "John Doe", // null if walk-in "items": [ { "product_name": "Wheat Flour 1kg", "barcode": "8901234567890", "unit": "kg", "quantity": 2, "unit_price_paise": 18000, "gst_rate": 18, "discount_percent": 0, "discount_paise": 0, "tax_amount_paise": 5492, "line_total_paise": 36000 } ], "tax_breakdown": { "0": { "rate": 0, "amount_paise": 0 }, "5": { "rate": 5, "amount_paise": 0 }, "12": { "rate": 12, "amount_paise": 0 }, "18": { "rate": 18, "amount_paise": 5492 }, "28": { "rate": 28, "amount_paise": 0 } }, "subtotal_paise": 36000, "total_discount_paise": 0, "total_tax_paise": 5492, "total_amount_paise": 36000, "payment_method": "cash", "status": "completed" }

Response (404 Not Found)

{ "detail": "Bill not found" }

Response (429 Too Many Requests)

Rate limiting enforced per IP address.

{ "detail": "Rate limit exceeded. Max 100 requests per hour." }

Rate Limiting Strategy

Protection against enumeration attacks

  • Limit: 100 requests per IP per hour
  • Implementation: Use Redis or in-memory cache with TTL
  • Header: Retry-After (seconds) in 429 response
  • Logging: Track rate-limit violations for security monitoring

Security Considerations

Data Exposure

  • Never expose customer phone/email/address on public page
  • Customer name only if set; default to "Customer" for anonymity
  • No user/cashier name exposed (user_id only in backend)
  • No payment card details, UPI IDs, or any sensitive payment info

Public Bill Page UI (Frontend)

Recommended Layout

  • Header: Invoice number, date, shop name
  • Items Table: Product, quantity, price, discount, tax, line total
  • Tax Summary: Grouped by rate (0%, 5%, 12%, 18%, 28%)
  • Totals: Subtotal, discount, total tax, final amount
  • Payment: Method (cash/card/upi) – no amounts
  • Mobile Optimized: Single column, readable on phone screens
  • Print-Friendly: CSS for clean printing without QR code or controls

7. Database Transaction Flow for Invoice Creation

Complete Atomic Flow

Validate Input
→
Fetch Products
→
Allocate Stock

Calculate Totals
→
BEGIN TRANSACTION
→
Create Invoice

Create Items
→
Deduct Stock
→
Record Movements

Generate QR Token
→
COMMIT/ROLLBACK

Transaction Phases

Phase 1: Pre-Transaction Validation (no database changes)

  • Validate payment method (cash, card, upi)
  • Validate discount percentages against user limits
  • Check if customer exists (if provided)
  • Verify user is active cashier/manager

Phase 2: Read Current State (queries, no locks needed)

  • Fetch products by ID or barcode
  • Get available batches (FEFO query)
  • Verify expiry dates (reject expired batches)
  • Calculate total needed stock

Phase 3: Prepare Invoice Data (in-memory calculation)

  • For each item:
    • Apply discount if provided
    • Extract tax by rate
    • Create snapshot fields
    • Calculate line totals
  • Sum invoice totals
  • Generate unique QR token

Phase 4: Atomic Transaction (all or nothing)

BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE 1. INSERT INTO invoices (...) RETURNING id as invoice_id 2. FOR EACH item: INSERT INTO invoice_items (invoice_id, ...) 3. FOR EACH item's stock allocation: UPDATE stock_batches SET quantity = quantity - allocation WHERE batch_id = ... 4. FOR EACH stock change: INSERT INTO stock_movements (...) 5. COMMIT If any INSERT/UPDATE fails → ROLLBACK all changes 6. If duplicate public_token → RETRY Phase 3 & 4

Transaction Isolation & Locking

Isolation Level: SERIALIZABLE

Ensures no concurrent transactions interfere with invoice creation or stock allocation. This is critical for preventing overselling.

Lock Strategy

  • Database acquires locks on StockBatch rows during UPDATE
  • If another transaction holds a lock, wait (or fail after timeout)
  • Consider adding application-level retry logic with exponential backoff

Error Handling Within Transaction

Error Action User Message
Product not found Rollback "Product not found. Verify barcode."
Stock exhausted Rollback "Insufficient stock for [Product]. Available: X units."
Batch expired Rollback "Batch expired. Cannot use this stock."
Duplicate public_token Retry entire flow Internal retry; transparent to user
Database constraint violated Rollback "Error creating invoice. Contact support."

8. Edge Cases & Considerations

Decimal Rounding Edge Cases

Scenario: Tax extraction with odd amounts

When tax_per_unit doesn't divide evenly, rounding errors accumulate. Solution:

  • Always round per-unit tax to nearest paise
  • Use standard banker's rounding (round half to even)
  • Accept that invoice total may differ from manual calculation by 1-2 paise
  • For reporting: verify tax grouping by rate sums correctly, not individual line exactness

Concurrent Transaction Conflicts

Scenario: Two invoices created simultaneously, both using same batch

With SERIALIZABLE isolation:

  • First transaction acquires lock on batch, creates invoice, commits
  • Second transaction's stock query sees updated batch quantity
  • If insufficient stock remains, second transaction rollbacks with clear error
  • Cashier retries with remaining available batches

Partial Stock Allocation (Multi-Batch)

Scenario: Product with 2 active batches (FEFO)

Customer orders 150 units; Batch A (expiry soon) has 80, Batch B has 100.

  • Allocate 80 from Batch A (nearest expiry)
  • Allocate 70 from Batch B (remaining)
  • Create two InvoiceItem entries? No – one line item.
  • Store batch_id as first batch used; note in audit trail if multi-batch
  • Stock movements record each batch separately for audit

Zero-Tax & Full-Discount Scenarios

0% GST Items

  • Tax extraction still runs; tax_amount_paise = 0
  • Line total = unit_price × quantity (no tax extracted)
  • Included in tax breakdown under "0% tax" grouping

100% Discount

  • Allowed only for manager role (if configured)
  • line_total_paise = 0
  • Stock still deducted (for inventory accuracy)
  • Tax still extracted (for compliance reporting)
  • Invoice can have zero or negative total_amount_paise

Invoice Cancellation & Returns

Cancellation (full reverse)

  • Mark invoice as CANCELLED (not deleted)
  • Return stock to original batch with reversing stock movements
  • Keep all original data intact for audit trail
  • Record cancellation reason and user in audit log

Partial Returns

  • Create new invoice marked as RETURNED with negative quantities
  • Link to original invoice via reference_id in stock movements
  • Recalculate tax and totals for return invoice
  • Return stock to inventory

Payment Method Validation

Cash Payment

  • amount_tendered_paise must be provided and ≥ total_amount_paise
  • change_due_paise calculated automatically
  • If amount_tendered < total_amount, reject transaction

Card/UPI Payment

  • amount_tendered_paise not required (assumed exact)
  • change_due_paise set to 0
  • Payment processing handled separately (not in this service)

QR Token Collision Handling

Very Rare: Duplicate Token Generated

  • Probability: ~1 in 10^30 with 128-bit random tokens
  • Application-level retry: Generate new token, check uniqueness, retry up to 5 times
  • Database unique constraint as last-line defense
  • If 5 retries fail, raise DataIntegrityError; user retries invoice creation

Invoice Number Sequencing

Format: INV-YYYY-NNNNNN

  • YYYY = Year (2026, 2027, etc.)
  • NNNNNN = Zero-padded sequence (000001 to 999999)
  • Sequence resets January 1 each year

Generation Method

  • Query maximum invoice number for current year from database
  • Extract sequence, increment by 1
  • Format and validate uniqueness before commit
  • Alternatively: use database sequence (recommended for concurrent performance)

Customer Loyalty Integration (Future)

Current Implementation

  • customer_id linked to invoice for loyalty tracking
  • Customer.loyalty_points field reserved for future loyalty system

Future Consideration

  • Award points per invoice based on amount spent
  • Apply points-based discount in future phase
